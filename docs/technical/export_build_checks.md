# Проверки экспортированной игры

`tools/northernlab_launcher.ps1 -BuildOnly` собирает Windows Dev во временный каталог. Готовая папка заменяется только после успешного экспорта и проверок; при ошибке предыдущая сборка сохраняется.

Вывод stdout и stderr записывается в журналы и показывается по мере поступления. Окно и рабочий процесс сборки разделены: окно обновляет журнал таймером WPF, сборка выполняется отдельным экземпляром оконного приложения. Оба размещают PowerShell внутри собственного процесса .NET, без `powershell.exe` и ConsoleHost. Чтением обоих потоков занимаются фоновые задачи из `tools/launcher/process_capture.cs`, без вызовов PowerShell с фоновых потоков. Принудительная прокачка событий `DoEvents` больше не используется. Если рабочий процесс завершается с ошибкой, окно показывает её и позволяет повторить сборку. Закрытие окна запрашивает отмену и ждёт освобождения дочернего процесса; предыдущая сборка сохраняется.

Ярлык `NorthernLab.lnk` запускает `tools/.local/NorthernLabLauncher.exe`, компилируемый из `tools/launcher/launcher_host.cs` как WindowsApplication. Изменения политики выполнения ограничены собственным процессом, как прежний параметр `-ExecutionPolicy Bypass`; настройки Windows не меняются. Godot, Git и Git LFS запускаются с `CreateNoWindow`, включая получение версии движка и сведений о ревизии. Журнал каждой попытки и её состояние находятся в `launcher-logs/sessions/<id>/` внутри локального каталога `tools/.local`; `ui-result.json` подтверждает код завершения рабочего процесса и доступность кнопки запуска. Для первого запуска из чистого проекта `northern_lab.cmd` создаёт оконный запускатель и ярлык.

Упаковка ресурсов ещё не означает готовность результата: следом выполняются проверки пакета, новой игры, сохранения и запуска EXE. Затем появляется этап публикации и сообщение `Build ready: build/windows-dev`. Рабочий результат — `build/windows-dev/NorthernLab.exe` вместе с DLL и сопроводительными файлами из этой папки.

Список экспорта содержит полное дерево зависимостей, найденное `tools/prepare_export_resources.gd`. Это необходимо в том числе для импортируемых шрифтов и вложенных тем. Одного списка сцен и скриптов оказалось недостаточно: отсутствие Roboto Condensed и темы вертолёта ломало загрузку `base_session.tscn` при создании игры, хотя главное меню работало.

Графические проверки также выявили удержание текстуры собственного курсора до завершения рендера. `GameMenu._exit_tree()` теперь снимает курсор со всех назначенных форм и освобождает статический кэш `NorthernMenuStyle`. Ошибки движка при закрытии учитываются проверками наравне с ошибками во время игры.

Быстрое закрытие главного меню также удерживало активный декодер музыки `main_menu.ogg`: движок завершался с кодом 0, но сообщал `2 resources still in use at exit`, поэтому публикация останавливалась. Проигрыватель явно освобождает поток при выходе из дерева. Штатный выход через GameMenu сначала освобождает текущую сцену и даёт серверам звука и отрисовки обработать освобождение, затем завершает движок. Кнопка выхода и закрытие окна используют этот путь. Проверка самого EXE передаёт `-- --startup-check` (только debug-сборки), проверяет главное меню и музыку, затем вызывает тот же штатный выход. Ошибки при закрытии по-прежнему останавливают публикацию.

Во время перехода из кабины и продолжения экспедиции физика игроков и расчёт выживания приостановлены до снятия загрузочного экрана. Восстановленные позиция в лифте, радиация и таймер респавна не изменяются во время прогрева сцены; после загрузки возвращаются прежние флаги обработки. Проверка — `expedition_resume_regression.gd`.

Перед публикацией автоматически выполняются:

- проверка наличия всех ресурсов из манифеста и загрузки их зависимостей;
- создание новой одиночной игры, появление персонажа и HUD в вертолёте;
- штатное действие готовности, переход на настоящую базу;
- сохранение и продолжение экспедиции;
- запуск самого игрового EXE.

Шаблон экспорта запрещает внешние скрипты и переопределение пути проекта. Поэтому проверки игровых действий запускают встроенный пакет EXE через соответствующий редактор с DLL именно из собранной поставки. Рабочий каталог находится вне исходного проекта; `project.binary` подтверждает использование пакета. Дополнительно запускается сам игровой EXE без внешних скриптов.

APPDATA и LOCALAPPDATA дочерних проверок перенаправлены в отдельный каталог. Тесты не используют настоящие настройки и сохранения игрока. Логи автоматической сборки: `tools/.local/launcher-logs/`.

В headless-запуске `BaseSessionController` загружает базу последовательно, а `level_load_job.gd` создаёт её в главном потоке. У dummy-рендерера Godot 4.7.2 хранилища RID материалов и шейдеров не защищены от одновременной работы потоков ([исходник движка](https://github.com/godotengine/godot/blob/4.7.2-stable/servers/rendering/dummy/storage/material_storage.h)). Фоновая загрузка или создание сцены одновременно с обработкой кадров могли вызвать `Attempting to initialize the wrong RID`, `material is null` и ошибки освобождения, даже если все условия игровой проверки прошли. В графическом запуске чтение ресурсов остаётся фоновым, а создание узлов выполняется в главном потоке: создание rendering-узлов в worker также воспроизводило `uniform_set is null` в Vulkan при расширенном освещении. На трёх одинаковых графических прогонах перенос создания узлов убрал ошибки. Это не устраняет тяжёлый кадр создания/присоединения общей сцены; его отдельно измеряет `loading_session_regression.gd`. Лаунчер по-прежнему отклоняет любые `ERROR`/`SCRIPT ERROR`, включая ошибки при завершении.

Расширенные проверки уже собранного пакета:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/tests/run_export_regressions.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/tests/run_export_regressions.ps1 -Graphical
```

Первый запуск проверяет настройки управления, слоты, восстановление экспедиции, полив, лифт и другие игровые действия. Второй проверяет настоящее меню с кликами, настройки, HUD на разных экранах и создание игры с отрисовкой. Результаты и снимки находятся в новом каталоге `tools/.local/export-audit-*`.

Проверка самого сборщика, блокировок DLL, публикации и отката:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File tools/tests/launcher_build_regression.ps1
powershell.exe -NoProfile -ExecutionPolicy Bypass -STA -File tools/tests/launcher_gui_regression.ps1
```

Проверки через тот же оконный хост, который использует ярлык:

```powershell
tools/.local/NorthernLabLauncher.exe --test-core
tools/.local/NorthernLabLauncher.exe --test-gui
tools/.local/NorthernLabLauncher.exe --test-full-gui
```

Последняя команда выполняет полную сборку в собственном тестовом окне вне экрана, проверяет работу диспетчера и включение кнопки «Играть» после публикации. Проверка окна также принудительно завершает тестовый рабочий процесс и проверяет, что окно остаётся доступным для повторной попытки; отдельно проверяется отсутствие консольного окна у дочернего процесса.

## Release для передачи

Отдельный пресет Windows Playtest использует то же замыкание зависимостей, что и Windows Dev, но release-шаблон и release-библиотеки. `tools/build_playtest.py` выполняет проверки встроенного пакета до создания установщика и portable. Настоящий EXE поддерживает явный аргумент `-- --startup-check` для проверки меню и штатного завершения; тестовые скрипты в поставку не входят. Описание: [версия для тестеров](../guides/distributing_playtest.md).
