# Сохранения и совместимость

Подготовка лебёдки сохраняется в `maintenance.winch_preparation` по отдельным шагам. Успех пробного цикла (`tested`) разрешает завершение шестого дня и спуск на седьмом. Сохранённый `testing` сбрасывается при чтении: незавершённая проверка не засчитывается. Для прежних сохранений дня 7+ без этого словаря подготовка считается пройденной; частично выполненная новая подготовка сохраняется без автоматического завершения.

Лебёдка использует отдельный `maintenance.winch_floor`; основной лифт сохраняет `maintenance.elevator_floor`. Позиции пассажиров и груза внутри транспорта содержат `in_cabin`, `cabin_id` и относительный Transform3D. Идентификатор совпадает с ключом транспорта: `winch_floor` либо `elevator_floor`. Прежние записи без `cabin_id` восстанавливаются в основном лифте. При записи в пути сохранённой остановкой остаётся отправление, поэтому после загрузки игрок и предметы оказываются в припаркованной клети, а не висят посреди шахты.

## Слоты и владение

Каталог проекта используется только при запуске исходников в редакторе, когда `res://` преобразуется в абсолютный путь. При проверке экспортированного пакета редакторным бинарником физического `res://` нет: в этом случае, как и в обычном EXE, используется каталог запущенного исполняемого файла. Путь сейвов остаётся абсолютным и не зависит от рабочей папки процесса.

Прогресс записывает и загружает хост. Клиент получает сетевое состояние и не подменяет его локальным файлом; отключение от сети не даёт клиенту право записи.

Меню показывает одну текущую одиночную и одну кооперативную экспедицию. Выбор отдельных экспедиций и переименование убраны из UI. Экран продолжения показывает три фиксированные точки выбранной экспедиции: ручную, утро текущего дня и утро прошлого дня. Существующее хранилище трёх слотов каждого типа остаётся для совместимости: файлы не удаляются при обновлении. При пустом активном слоте главный экран/создание кооператива выбирают наиболее свежий действительный сейв через `select_existing`. Лимит сессии остаётся два игрока.

| Каталог / настройка | Назначение |
| --- | --- |
| `<каталог игры>/saves/expeditions/solo_1` … `solo_3` | Одиночные слоты |
| `<каталог игры>/saves/expeditions/coop_1` … `coop_3` | Кооперативные слоты на компьютере хоста |
| `northern_lab/testing/base_save_path` | Изолированный одиночный файл старых профильных тестов |
| `northern_lab/testing/save_slots_root` | Изолированный корень тестов слотов |
| `northern_lab/testing/legacy_save_paths` | Явные тестовые исходники миграции; обычные сейвы тестами не читаются |

В экспортированной игре каталог определяется по расположению исполняемого файла, независимо от рабочей папки запуска. При запуске из редактора используется `<корень проекта>/saves/`, а не папка редактора Godot. Личные записи журнала находятся рядом в `saves/journal_reading/`. Настройки графики, управления и отзывы тестеров остаются в `user://` — пользовательских данных Godot. Папка `saves` исключена из Git и поставки тестерам.

Прежние каталоги `user://expeditions/` и `user://journal_reading/` автоматически не переносятся. Чтобы продолжить такое прохождение, скопируйте их в `saves/` нужного билда при закрытой игре. Исходные файлы остаются на месте. Для записи нужна доступная на запись папка игры; при отказе записи используется существующая обработка ошибки сохранения.

Основная логика остаётся в `BaseGameplayController` и `BaseSessionController`; `ExpeditionSaveStore` обслуживает файлы, слоты и историю. Инвентари и состояние участников привязаны к Steam ID, а не к порядку подключения. В одиночной игре используется идентификатор `solo`.

Слоты остаются у прежнего хоста. Передачи роли хоста, переноса экспедиции на другой компьютер и Steam Cloud эта задача не добавляет.

Для продолжения прежний хост создаёт кооператив и выбирает «Продолжить», затем напарник подключается к новой сессии со своего прежнего Steam-аккаунта. Номер сетевого peer может измениться: данные ищутся по аккаунту. Для входа требуются совместимые сборки; проверка сетевой совместимости не является проверкой совместимости старого сейва с изменённой геометрией уровней.

Если напарник выходит раньше хоста, `BaseSessionController._on_peer_left()` выгружает его снаряжение возле назначенной койки и обновляет данные повторного входа в памяти хоста, не записывая мир на диск. При возвращении предметы следует искать там, а не ожидать прежний предмет в руках: это существующее правило отключения, а не отдельный личный сейв гостя. Положение и показатели выживания остаются в записи участника. Фактическое сопоставление Steam ID при потере соединения требует проверки настоящим Steam-транспортом; ENet-тесты используют стабильный тестовый идентификатор.

## Три точки продолжения

Игроку доступны три фиксированные записи внутри экспедиции:

- Ручная запись: одна успешная запись за игровой день. Действует только до следующего утра; сон освобождает возможность и убирает вчерашнюю ручную запись из доступных точек.
- Утро текущего дня: полный снимок после пробуждения, восстановления здоровья и перемещения игроков к койкам. На первом дне используется стартовый снимок после появления предметов.
- Утро прошлого дня: предыдущий утренний снимок. Более старые утра не предлагаются. Пропущенные debug-переходом дни не создают выдуманные точки.

`manual_save_day` входит в снимок мира и передаётся всем участникам. Хост проверяет его перед записью; файловое хранилище также отвергает вторую ручную запись за тот же день. Ошибка записи не расходует возможность. Повторная загрузка ручной записи не возвращает возможность сохраниться. При выборе утра нынешнего дня уже использованная возможность также сохраняется, хотя последующая ручная ветка отбрасывается. Возврат к утру прошлого дня начинает прежнюю ветку с её утренним состоянием. Ещё более раннее утро не восстанавливается из технических резервов: нижняя строка остаётся пустой до следующего сна.

Экран «Продолжить» показывает три строки с днём и питанием; пустые точки отключены. При открытии выбрана последняя действительная запись. Нажатие строки меняет только выделение и действие загрузки; основная кнопка загружает выбранную запись. Загрузка более раннего утра требует подтверждения и атомарно заменяет текущую ветку; будущая ручная запись и более поздние утра исчезают из доступного списка. Одиночная игра и создание кооператива используют один экран. Выбор точки кооператива доступен хосту до начала сессии, а не во время игры.

В ESC кнопка ручной записи доступна хосту, когда дневная возможность ещё не использована и закончился переход на базу. Подпись объясняет лимит и истечение после сна. Гость видит общий статус команды; его локальная кнопка записи отключена. Лимит общий для экспедиции, не отдельный для каждого игрока. Даже после потери соединения клиент не приобретает право сохранять мир.

## Только явная запись и утро

Пятисекундный таймер, очередь записи инвентаря и автоматические записи при изменениях базы, подборе/передаче/выбросе предметов, перемещении тяжёлых объектов, сборке, использовании терминала и снегохода удалены. Изменения продолжают реплицироваться по сети и входят в следующий полный ручной или утренний снимок. Сюжетные события не создают дополнительных контрольных точек.

Возврат в меню, штатное закрытие, отключение гостя и завершение сессии не записывают прогресс и не создают временного сейва. UI предупреждает о потере изменений после последней записи. При отключении гостя данные для повторного входа остаются только в памяти хоста; следующий разрешённый сейв захватывает оставленные вещи и состояние обоих аккаунтов. Идентификатор Steam кэшируется на время подключения, чтобы обработка разрыва не записывала снаряжение под временным peer ID.

При ручной и утренней записи отображается «Сохранение… Не закрывайте игру», затем подтверждение либо сообщение об ошибке. В кооперативе хост передаёт уведомление обоим участникам надёжным RPC; поздний вход не повторяет старое уведомление.

`scenes/ui/save_notification.tscn` — штатный индикатор поверх игры и ESC. Анимация пользователя из `loading.svg` запечена в `assets/ui/save_indicator/loading_atlas.png` и `loading_frames.tres`: 180 кадров, 30 кадров/с, петля 6 секунд. Исходник хранится под `.gdignore`; `tools/bake_save_indicator.cjs` повторяет подготовку. Минимальное время показа — 0,7 с, результат остаётся на экране 4 с; это не задерживает запись.

По обращению #18 подтверждение теперь остаётся 4 секунды и расположено по центру сверху, ниже компаса. Минимальное время фазы записи и правило одной ручной записи за день не изменены. Тест уведомления перед повторным сном ожидает окончания штатной анимации подъёма; немедленный повтор во время неё намеренно запрещён.

## Целостность записи

Каждая запись — новый неизменяемый `commit_*.cfg`. Сначала записывается временный файл, вызывается `flush`, проверяется записанный текст, затем файл публикуется переименованием. Снимок мира и ссылки на историю публикуются вместе. Незавершённый `.tmp` не считается сохранением.

Контрольная сумма SHA-256 проверяет содержимое и историю. При повреждении последней записи загрузчик выбирает предыдущую проверенную; меню сообщает о восстановлении из резервной копии. Хранятся две последние корректные записи и необходимые им контрольные точки; старые файлы удаляются после успешной публикации. Эти технические резервные копии не расширяют доступную игроку историю отката.

Формат игровых данных сохраняет `SAVE_VERSION = 1`; файловая оболочка имеет собственную версию. Версия игры, формат сейва и сетевой протокол имеют разные назначения. Повышение версии приложения не сбрасывает прохождение.

## Содержимое и восстановление

Сохраняются день, сюжетные флаги, питание, топливо, обслуживание, здоровье и тела сюжетных монстров, медицинский перенос, инвентари и оставленные предметы, снегоход и открытые ворота. Для участников сохраняются позиция, направление, здоровье, радиация, смерть и остаток времени до возрождения. Загрузка не лечит живого игрока и не отменяет его смерть.

Положение лифта сохраняется как этаж безопасной остановки. При сохранении во время движения загрузка паркует кабину на этаже отправления с открытыми дверями. Игроки и предметы внутри восстанавливаются относительно кабины; загрузка не пытается продолжить незавершённый переход между этажами. Параметры остановок и геометрия остаются в сценах движка.

Готовность ко сну и незавершённая перезарядка не восстанавливаются. Сон возобновляется как обычное состояние игрока в точке начала дня. Водитель загружается пешком у существующего безопасного маркера выхода снегохода; если оба выхода заняты, используется штатная точка возрождения. Сам снегоход и его топливо сохраняются. Фонарик выключается и убирается в карман. При сохранении во время переноски тело восстанавливается свободным рядом с последним положением носильщика.

Следы снега, попаданий, локальные звуки, скорости физического лута и промежуточные состояния художественных анимаций не сохраняются.

Установка предохранителя резерва лифта сохраняется как `elevator_backup_installed`, вместе с инвентарём, из которого предмет уже израсходован. `elevator_backup_layout_version` предотвращает повторное появление предохранителя. Старые сейвы первого дня получают недостающий предмет однократно; после первой ночи резерв считается подключённым, сохраняя прежний доступ к лифту.

Ежедневный полив хранится как `plant_last_watered_day`: последний игровой день подтверждённого действия, общий для экспедиции. Старый файл без поля получает 0. Загрузка восстанавливает доступность кнопки и индикатор, но не повторяет полив, звук или частицы. Сон открывает возможность полива нового дня; ручная запись и отключение питания лимит не сбрасывают. Подробнее: [контейнер растений](base_gameplay_state.md#контейнер-растений-и-ежедневный-полив).

## Старые сохранения и изменение формата

Совместимые `user://base_gameplay_state.cfg` и `user://base_gameplay_state_coop.cfg` автоматически копируются в первый слот своего режима. Исходные файлы остаются нетронутыми. Маркер миграции предотвращает повторный импорт после очистки слота. Сейвы без новых данных участника используют прежние точки появления и здоровье по умолчанию.

Версии раскладки инвентаря добавляют недостающие начальные припасы однократно. `campaign_layout_version` переносит прежнюю объединённую встречу на отдельные дни. Старые пути невидимых медицинских коек переводятся на фактические койки медкомнаты.

Перечисленные миграции уже существуют в коде. На текущем этапе команда сбрасывает сейвы после крупных изменений; новые миграции раскладки и расписания дней не требуются. Проверяйте сохранение и продолжение текущей версии. Значение по умолчанию для отсутствующего поля остаётся полезным, но не заменяет это правило совместимости. F6 отключает обычную запись прогресса.

## Проверки

- `checkpoint_write_coalescing_regression.gd`: отсутствие дисковых записей при изменении инвентаря/мира и ожидании пяти секунд, один ручной сейв, выход без записи и восстановление дневного лимита. Имя файла оставлено для существующего запуска; прежняя очередь объединения записей удалена.
- `save_location_regression.gd`: расположение сейвов в редакторе и экспортированном runtime, запись/чтение одиночного и кооперативного прогресса, личный журнал и тестовые переопределения путей.
- `expedition_save_slots_regression.gd`: изоляция слотов, имена, дневной лимит, истечение ручной записи, два последовательных утра, откат с удалением будущей ветки, повреждение файла, незавершённая и неудачная запись.
- `expedition_resume_regression.gd`: настоящая база, сохранение в движущемся лифте, восстановление игрока и лута, сон, здоровье и смерть.
- `expedition_menu_regression.gd`: три точки продолжения, пустые состояния, подтверждение отката, общий экран кооператива, сохранность других экспедиций и кнопка ручной записи.
- `save_notification_regression.gd`: реальные ручная запись, неудачная запись, отмена сна и успешная ночь; отказ фоновой записи, проигрывание кадров, подтверждение и автоматическое скрытие. Графический запуск сохраняет кадры в `tools/.local/save-notification-review`.
- `python tools/tests/run_expedition_multiplayer.py`: два процесса ENet с production-сессией, поздний клиент, инвентарь, здоровье, положение и сюжет хоста, запрет локальной записи клиента даже после отключения. Стабильные аккаунты в этом ENet-тесте имитируются отдельной тестовой реализацией идентификатора; настоящий Steam транспорт требует ручной проверки.
- `python tools/tests/run_expedition_restart_multiplayer.py`: первая пара ENet-процессов записывает изменённое состояние живой команды; после полного закрытия запускается новая пара, читающая тот же файл. Проверяются оба инвентаря, остатки патронов/топлива, HP/радиация, относительные позиции в лифте, сюжет, новые флаги журнала, полив и отсутствие повторного лута. Затем гость действительно отключается, а следующее утро хоста сохраняет оставленную канистру в мире и пустые руки аккаунта. Первая фаза закрывается на явно зафиксированном снимке без последующих записей; этот тест не нажимает пункты Steam-меню и не подтверждает внешний транспорт. Все файлы изолированы от пользовательских экспедиций.

Дополнительно проходят существующие проверки дней, резерва лифта и меню. На двух компьютерах с разными Steam-аккаунтами проверить сохранение хостом, выход обоих, продолжение текущей экспедиции, подключение прежнего напарника, отсутствие повторного лута, затем ручное сохранение из ESC, отказ повторной записи, общий сон и выход без записи.

## Перестановка этажей

После добавления испытаний на уровень 3 начните новую экспедицию. Биосдерживание стало уровнем 4, шахта — уровнем 5, их координаты Y смещены на −18 м. Перенос старых позиций и индексов сохранений намеренно не реализован по решению команды на этапе прототипа. Это не меняет формат внутреннего хранилища новых сохранений. Внутренний ключ `containment.level3` остаётся идентификатором обследования биосдерживания и не равен текущему номеру этажа.

Новый маршрут использует дни 1–7. Проверка новых файлов принимает дни 6 (шахта) и 7 (пещера); обследование камеры сохраняется как `containment.trials`. Отдельная совместимость с прежним расписанием дней не добавлена. День 6 завершается посещением зала лебёдки и сном. День 7 использует `containment.cave_visited` для посещения нижней шахты; прежний `cave_exited` остаётся допустимым для уже сохранённого прохождения.

Посадка хранится в общем поле `plant_seed_planted` (по умолчанию false). Семечко расходуется из обычного инвентаря; пакет в мире сохраняется через существующий checkpoint предметов. После посадки загрузка и позднее подключение восстанавливают конечный вид контейнера без повторной анимации. Новая экспедиция сбрасывает посадку.

Рост растения сохраняется в `plant_growth_stage` (0–7), гибель — в `plant_withered`. Оба поля общие для экспедиции. День в валидации сохранения и контроллере использует единый `ExpeditionSaveStore.MAX_DAY_INDEX = 999`, чтобы обычный сон после пещеры сохранял дни 8+ и позволял закончить позднюю посадку. `containment.shaft` и `containment.cave_exited` сохраняются прежним словарём обследования. История контрольных точек и совместный сон работают по прежним правилам.

Кликер терминала сохраняется в общем поле `lab_clicker` (баланс `samples` и исходные количества `owned`). Производные доходы и цены вычисляются из ресурсов улучшений. Прогресс общий для экспедиции, записывается хостом обычным механизмом сохранения. Доход работает только во время запитанной игровой сессии; офлайн-начислений нет. Подробнее: [Lab Clicker](lab_clicker.md).


## Исходы встречи с монстрами

`containment.monster_outcomes` хранит нелетальные исходы сюжетной тройки: причина, скрыт ли экземпляр, конечная позиция и ориентация. После загрузки такой монстр не оживает и не превращается в погибшего. Отсутствующее поле в старом сейве означает отсутствие нелетальных исходов. Сохранённые тела содержат `rig_id`: несовместимая с новым скелетом поза не применяется, тело заново успокаивается у хоста. Старые записи без сигнатуры принимаются с проверкой числа тел. Отладочные `/spawn` не являются постоянными существами экспедиции.


Расставленные патрули Monster3/4 записывают HP в отдельный `containment.patrol_health`, а позы — в прежний словарь `bodies`. Отсутствие нового поля в старом сейве даёт стартовые HP двух новых существ; их смерть затем сохраняется. Сюжетная тройка и её условия завершения используют прежние индексы 0–2. Дополнительный лут мигрирует через `inventory.base_supply_layout_version = 1`; после сохранения маркер версии запрещает повторное добавление припасов. Пути файлов сохранений не менялись.
