# Архитектура

## Загрузка мира

```mermaid
flowchart TD
    Menu[Главное меню] --> Session[base_session: вертолёт и сетевая сессия]
    Session --> Base[Base_Blockout_v03: сборка базы]
    Base --> Floors[Уровни 0–5]
    Base --> Exterior[SnowExterior и Terrain3D]
    Base --> State[BaseGameplayController]
    State --> Systems[Питание, дни, койки, задания и встреча с монстрами]
```

Главное меню запускает одиночную или Steam-сессию. `BaseSessionController` ведёт roster игроков, переход и обмен первоначальными состояниями. База сохраняет исходные сцены этажей; `BaseBlockoutRuntime` связывает игровые объекты, создаёт припасы и обслуживает тестовый запуск.

Задание `level_load_job.gd` принадлежит сессии: оно получает сцену, собирает отсоединённые части и восстанавливает коллизии. `_exit_tree()` сессии отменяет задание; отсоединённые узлы освобождает задание, присоединённые — сцена. Завершившийся нативный запрос читается и при отмене, но его результат не публикуется. `GameMenu` использует поколение перехода и `is_loading_world()`, поэтому закрытая сессия не должна завершать новый переход. Ошибка загрузки рельефа возвращает в меню через `abort_scene_load()`.

## Компоненты персонажа

| Компонент | Ответственность |
| --- | --- |
| `GamePlayer` | Узел `CharacterBody3D`, настройки Inspector, серверное выполнение команд, RPC и координация компонентов |
| `PlayerLocalInput` | Локальные устройства, направление движения/взгляда и фронты команд |
| `PlayerLocomotion` | Перемещение тела, приседание, запас бега и шум шагов |
| `PlayerStateReplication` | Отправка и применение снимков, интерполяция и коррекция позиции |
| `PlayerEquipment` | Состояние предмета в руках и фонарика |
| `PlayerSupplies` | Карманные запасы, батареи и атомарный расход рецептов |
| `PlayerInventoryActions` | Синхронные операции подбора, смены, расходования и выбрасывания; состояние не дублирует |
| `GameCharacterPresentation` | Визуальное представление своего и удалённых персонажей |
| `ItemHandoff` | Предложение, срок, токен, проверка участников и совместная публикация передачи |

Компоненты данных и расчётов — `RefCounted`, без дополнительных узлов или Autoload. Они не хранят сильную обратную ссылку на игрока. `PlayerInventoryActions` содержит статические команды. Анимационные ожидания остались на узле персонажа; RPC, пути сцен и формат сохранений сохранены. Старые свойства `GamePlayer` делегируют единственным владельцам данных и поддерживают существующие подключения. Представление получает состояние экипировки и признаки видимости явно, не изменяя внутренние поля игрового состояния.

Результаты завершённого прохода и ограничения проверки: [архитектурный отчёт](technical/architecture_completion_2026_11_14.md).

Перечень определяется `project.godot`. Журнал и меню не владеют сюжетным состоянием.

## Владельцы состояния

| Данные | Система |
| --- | --- |
| День, топливо, питание, задания, обслуживание | `BaseGameplayController` |
| Игроки и сохранённый инвентарь участников | `BaseSessionController`, `GamePlayer` |
| Движение, здоровье, расход предметов и попадания | Авторитетный хост |
| Кабина, двери лифта и текущая поездка | `FunctionalElevatorController` |
| Здоровье сюжетных монстров и сбой питания | `ContainmentEncounter` совместно с состоянием базы |
| Переносимое тело и занятая койка | `MedicalCorpse`, секция обслуживания базы |
| Громкость, камера, UI и локальные эффекты | Клиентские компоненты |

События меняют состояние на хосте, затем снимки применяются участниками. Сигналы базы связывают питание, двери, свет и интерфейс. Не следует добавлять параллельный флаг питания или отдельную копию задания в UI.

## Сцены и ресурсы

`scenes/art` содержит визуальные части. `scenes/objects` — объекты с логикой и коллизиями. `scenes/characters` — игрока, монстров и ragdoll. Профили ИИ находятся в `assets/config/monsters`. Inspector содержит изменяемые параметры и ссылки на сцены/звук; сохраняемый прогресс передаётся отдельно.

В проекте также остаются временные решения: runtime-привязка объектов базы, часть CSG-геометрии и несколько процедурных эффектов; навигация уровня 4 теперь запекается офлайн. Их наличие само по себе не требует переписывания. Изменение оправдано конкретной проблемой загрузки, расширения или поведения.

## Границы расширения

Для нового предмета используйте существующий тип и состояние pickup либо расширьте общий механизм. Для нового существа подготовьте сцену, модель, ragdoll и профиль. Для нового задания определите сохранение, переход между стадиями и представление журнала. Для нового уровня сохраните договорённости лифта, spawn-маркеров и координат.

См. [сохранения](technical/save_system.md), [сеть](technical/steam_networking.md), [Inspector](technical/inspector_gameplay_tuning.md).
