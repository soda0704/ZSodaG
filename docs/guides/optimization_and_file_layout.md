# Оптимизация и размещение файлов

Рабочие правила NorthernLab для двух разработчиков. Документ объединяет порядок файлов, безопасные изменения ресурсов и проверку производительности. Актуализирован 27 октября 2026.

Подробности: [имена и переименования](naming.md), [реализация оптимизаций](../technical/project_optimization.md), [замеры и ограничения](../technical/performance_baseline.md), [проверки](testing.md).

## Имена

Файлы и папки собственных исходников называются в `lower_snake_case`: только нижний регистр, слова через `_`, без пробелов. Для новых имён используем латиницу и смысловые названия вместо `new`, `final_final`, `copy_2`.

Примеры:

```text
fuel_can_pickup.tscn
day_two_terminal.gd
terminal_screen.gdshader
floor_0_base_blockout.tscn
```

Существующие имена не нужно массово приводить к новому шаблону ради косметики. Имя файла не требует переименования класса, узлов, костей, анимаций, NodePath, групп, действий ввода, Steam ID или ключей сохранений. Эти идентификаторы имеют собственные зависимости.

Технические имена Godot, Git и сторонних форматов сохраняются: `project.godot`, `.gdignore`, `.gitignore`, `plugin.cfg`, расширения `.gd.uid` и `.png.import`. В именах регионов Terrain3D минус обозначает координату: `terrain3d-01_02.res` нельзя превращать в имя с одними подчёркиваниями. Содержимое сторонних пакетов не переименовываем без отдельной необходимости и проверки.

## Куда класть файлы

| Каталог | Содержимое |
| --- | --- |
| `scripts/` | Runtime-код существующих подсистем: gameplay, персонажи, сеть, уровни, UI, ввод и эффекты |
| `scenes/levels/` | Сборки уровней и игровые точки входа |
| `scenes/objects/` | Повторно используемые игровые объекты с логикой и коллизиями |
| `scenes/art/` | Визуальные сборки помещений, окружения и объектов |
| `scenes/ui/` | Сцены интерфейса |
| `scenes/characters/` | Сцены персонажей |
| `assets/config/` | Конфигурации и ресурсы данных |
| `assets/models/` | Готовые игровые модели; зависимые текстуры сохраняем рядом с моделью |
| Остальные тематические папки `assets/` | Анимации, звук, шейдеры, материалы, окружение и UI-ресурсы |
| `blender/` | DCC-исходники и подготовка контента, исключённые из игрового импорта |
| `tools/authoring/` | Повторяемые инструменты подготовки ресурсов |
| `tools/tests/` | Сохраняемые проверки и профили производительности |
| `tools/.local/` | Игнорируемые временные прогоны, кадры, логи и локальные инструменты |
| `docs/guides/` | Рабочие инструкции |
| `docs/technical/` | Устройство реализованных систем и технические ограничения |
| `docs/reviews/` | Результаты конкретных аудитов и миграций |

Сначала ищем подходящую существующую папку. Не создаём параллельные `new_system`, `misc` или новый manager, если задача укладывается в имеющуюся систему. Модель, её текстуры и лицензия должны сохранять понятную связь; отделять текстуры из glTF по всему проекту ради общего каталога не нужно.

`.godot/` — локальный кэш движка, `build/` — результат сборки. Их не смешиваем с авторскими ресурсами. Сохранения находятся в папке игры `saves/`, при запуске из редактора — в корне проекта. Не добавляем их в Git, не включаем в поставку и не используем реальные прохождения для тестов. Подробности — [система сохранений](../technical/save_system.md).

## Безопасное перемещение и переименование

1. Проверить Git, сохранить текущие изменения и при необходимости сделать резервную копию вне проекта.
2. Найти прямые, вычисляемые и относительные ссылки. Составить карту старых и новых путей, проверить совпадения имён и регистра.
3. Предпочитать операции через FileSystem Godot. При скриптовой миграции переносить связанные `.uid` и `.import`, сохранять UID и настройки импорта, обновлять ссылки одновременно.
4. Текстовые сцены, скрипты, glTF URI и инструменты проверять отдельно от бинарных ресурсов. `.res` изменять средствами Godot, `.blend` — средствами Blender; побайтовая замена путей для них недопустима.
5. Выполнить импорт и проверку зависимостей. Протестировать затронутую механику, новую игру и продолжение. После изменения экспортных путей собрать и запустить пакет.
6. Передавать напарнику завершённую миграцию вместе со всеми ссылками, а не отдельный коммит с перемещёнными файлами без исправленных зависимостей.

Удаление по совпадению имени или хеша запрещено: одинаковые файлы могут иметь разные ссылки и настройки импорта. Для legacy сначала проверяем сцены, бинарные ресурсы, вычисляемые загрузки и инструменты подготовки; при сомнении фиксируем кандидата, а не удаляем его.

## Как оптимизировать

Сначала воспроизводим конкретную проблему и измеряем её. Отдельно рассматриваем чтение ресурсов, создание сцены, подключение к дереву, первый показ, постоянную стоимость кадра и сетевые задержки. Средний FPS не показывает одиночный сильный фриз.

Для сравнения фиксируем движок, рендерер, оборудование, разрешение, настройки, ракурс, маршрут, прогрев, VSync и ограничение FPS. Записываем медиану, p95/p99 и максимум времени кадра. Замеры не запускаем одновременно со сборкой, импортом или другим тяжёлым тестом. Результаты RTX 5080 не считаем подтверждением работы на слабом CPU или в Steam-сессии.

Каждое изменение должно сохранять игровые правила и проверяемый внешний вид:

- Не выключать физику, AI, состояние мира и коллизии по камере хоста: рядом может находиться второй игрок или удалённый предмет.
- Визуальную анимацию приостанавливать только при подтверждённой невидимости; учитывать открытые двери и вид из соседнего помещения. Близость сама по себе не доказывает невидимость.
- Объединять только действительно одинаковые статические материалы. Управляемые индикаторы, экраны и материалы с индивидуальным состоянием должны сохранять независимость.
- Сжатие текстур, LOD, тени и дальности менять после измерения и сравнения изображения. Не выдавать снижение качества за бесплатное ускорение.
- UI обновлять по изменениям данных, где это подходит. У экранов через SubViewport проверять фактическую текстуру каждого экземпляра, а не только сохранённый путь.
- Свет, материалы, размещение, UI-разметку и художественную анимацию настраивать штатными ресурсами и редактором. Код использовать для поведения и необходимой интеграции.

## Что уже сделано и что важно сохранить

В хабе включено штатное более точное отсечение отбрасывателей теней и объединены 80 точных копий статического материала пола. В проверенных ракурсах draw calls уменьшились на 19,5–30,6%. Это результат конкретного профиля прогретой сцены, а не обещание такого же прироста FPS везде.

Подготовка базы распределена между кадрами в существующем переходе. Создание Node остаётся на главном потоке; фоновое чтение ресурсов не заменяет распределение тяжёлой инициализации. Сохраняются все этажи, 48 регионов Terrain3D, полные коллизии мира и продвинутое освещение. Поэтапная загрузка не является бесшовной: после визуальных исправлений максимум в контрольном запуске исходного проекта — около 0,39 с, в отдельном запуске EXE — около 0,61 с. Подробные условия находятся в [замерах](../technical/performance_baseline.md).

`assets/config/level_loading_plan.res` — производный план загрузки. Его обновляет `tools/prepare_level_loading.gd` перед экспортом через launcher; вручную редактировать план вместо исходных сцен не нужно. Устаревшая сохраняемая часть плана должна приводить к безопасной обычной сборке сцены, а не загрузке старого содержимого.

При восстановлении переопределений нельзя терять native-контекст scene-local ресурсов: у ViewportTexture должен оставаться свой терминал. После позднего подключения Terrain3D необходимо восстановить его участие в наружном освещении. Именно эти зависимости ранее дали постороннее изображение на терминале и неверную яркость окружения; одного сравнения свойств сцены для их обнаружения недостаточно.

## Проверка перед передачей изменений

Из корня проекта:

```powershell
python tools/normalize_project_paths.py --check
python tools/check_documentation.py
```

Первая команда проверяет имена, вторая — документацию. Они не доказывают работоспособность gameplay. Для затронутых систем нужны соответствующие проверки и осмотр в игре; конкретные команды описаны в [руководстве по тестированию](testing.md).

Для загрузчика используем `level_load_equivalence_regression.gd` и графический `loading_session_regression.gd`: состав и связи сцены, owning scene у ViewportTexture, реальные пиксели обоих экранов, приём солнца и физика всех регионов. После изменения упаковки проверяем готовый EXE вне исходного проекта. Отсутствие ошибок в Console не заменяет осмотр изображения.

## Работа вдвоём

Gameplay-разработчик может самостоятельно подключать готовые модели, собирать игровые сцены, настраивать коллизии, ссылки, точки взаимодействия и простые анимации. Для этого не требуется искусственная передача art-задачи. Финальный художественный polish и сложный новый контент рационально согласовывать со вторым разработчиком.

Не редактируем одну сцену или бинарный ресурс одновременно без согласования. Изменения делаем локальными, зависимости передаём вместе, затронутую документацию обновляем после фактической реализации. Массовая реорганизация проекта и рефакторинг ради порядка не являются обязательной подготовкой следующей gameplay-задачи.
